# 九轩阁 MAIC V6 项目卡与个人项目测评合同

日期：2026-07-28

适用 Gate：

```text
Gate 3 项目卡、讨论与双档案
Gate 4 个人项目测评与异步评价
```

状态：产品合同已冻结，正式实现尚未开始

## 1. 核心结论

[DECIDED, HIGH] 项目卡不是企业全量资料库，也不是聊天记录容器。它是：

> 由案主确认、可被学员理解、可被 Agent 安全调用、可被后续课程持续引用的企业上下文基线。

[DECIDED, HIGH] 个人项目测评不是 OpenMAIC 课堂中的互动，也不是项目讨论。它是：

> 基于冻结项目卡和当前课程概念，检验学员能否独立完成事实判断、假设检验、方案比较、因果推理和判断修正的独立测评。

[DECIDED, HIGH] 每门课程可配置 3-6 道开放场景题，不要求所有课程使用相同题型。商业模式首发仍配置 6 题，沿用“两次正式提交、测试时无 Agent、无数字总分”的既有决定。

## 2. 对象边界

```text
项目空间
├── 项目卡
├── 个人研习
├── 小组讨论
├── 个人项目测评
├── 个人学习档案
└── 标的项目档案
```

| 对象 | 核心主体 | 保存内容 | 不保存内容 |
|---|---|---|---|
| 项目卡 | 标的项目与案主 | 企业上下文、事实、判断、假设、未知项、材料、课程结论 | 个人聊天、共享聊天、测评答案 |
| 个人研习 | 学员 | 私有对话与个人笔记草稿 | 正式项目结论 |
| 小组讨论 | 项目组 | 共享讨论消息与讨论摘要 | 个人测评答案 |
| 个人项目测评 | 学员 | 冻结题目、独立回答、两次提交、评价 | 实时 Agent 帮答、个人/小组讨论历史 |
| 个人学习档案 | 学员 | 个人笔记、测评与反馈 | 未经授权的项目组共享内容 |
| 标的项目档案 | 标的项目 | 经确认沉淀的观点、假设、作业和结论 | 自动复制的个人私有对话 |

## 3. 项目卡七个内容模块

### 3.1 项目身份与治理

必填：

```text
project_id
项目名称
企业名称或案例别名
案主 user_id
所属行业
主要经营区域
企业发展阶段
信息截止日期
保密等级
项目状态
```

系统生成：

```text
项目创建时间
项目卡版本 ID
版本号
创建方式 learner_form | admin_import
导入引用 import_ref
案主确认状态
审核与发布时间
```

约束：

- 案主是 `project_membership.role = target_owner`，不是全局角色；
- 动态成员关系由独立 membership 保存，项目卡不覆盖历史关系；
- 后台导入只生成 `draft + pending owner confirmation`。

### 3.2 企业基本业务信息

最小字段：

```text
一句话业务定义
主要产品或服务
主要客户
核心价值主张
主要交易方式
收入来源
主要渠道
关键合作方
关键资源与能力
主要业务线
```

一句话业务定义使用：

```text
我们为【目标客户】，解决【核心问题】，通过【产品或服务】完成交付，
并通过【交易方式】获得收入。
```

### 3.3 当前经营快照

最小字段：

```text
当前营收规模或区间
近一年营收趋势
主要增长来源
盈利状态
现金流状态
主要客户结构
当前组织规模
当前交付规模
当前主要瓶颈
未来 12 个月目标
```

精确经营数据允许转换为区间。区间化后的值与原始值必须分开保存，并分别设置模型使用权限。

### 3.4 本次项目核心问题

最小字段：

```text
当前核心问题
问题背景
希望形成的决策
决策时间范围
关键约束
已尝试动作
当前候选方案
案主最担心的风险
希望项目组提供的价值
```

推荐问题结构：

```text
在【时间范围】内，在【关键约束】条件下，企业应如何在【选项 A】与
【选项 B】之间进行选择，以实现【目标】，并控制【核心风险】？
```

### 3.5 事实、案主判断、假设与未知项

四类内容必须物理分开：

```text
verified_fact
owner_judgment
hypothesis
unknown
```

已验证事实至少保存：

```text
fact_id
内容
所属课程主题
数据日期
来源
验证状态
敏感级别
model_policy
```

案主判断必须说明依据，但不得自动升级为事实。

待验证假设至少保存：

```text
hypothesis_id
内容
提出人
提出原因
支持证据
反对证据
需要什么信息验证
状态
```

假设状态：

```text
pending
partially_verified
verified
rejected
revised
```

未知项必须能转化为后续补充资料、Agent 追问或测评中的验证任务。

### 3.6 企业材料目录

项目卡只保存材料元数据和引用，不把全部文件正文直接写入卡片或模型上下文。

每份材料至少保存：

```text
asset_id
材料名称
材料类型
提供人
数据日期
摘要
关联课程主题
可见范围
model_policy
文件版本
storage_key
checksum
```

首版建议案主提供 3-10 份关键材料。合同、客户名单、个人信息和完整财务原文默认不进入外部模型。

### 3.7 前序课程结论

初始创建时可以为空。每门课完成后按版本写入：

```text
course_id
结论标题
结论内容
引用事实 ID
相关假设 ID
支持意见
反对意见
当前置信度
未解决问题
来源作业版本
评审状态
形成时间
```

课程结论不是已验证企业事实。后续课程可以引用、挑战、修订或替代，但不得原地改写历史结论。

## 4. 项目卡版本与发布

状态机：

```text
draft
→ owner_confirmed
→ published
→ superseded
→ archived
```

发布规则：

1. 项目卡由案主填写，或由教务导入草稿；
2. 案主逐项确认、修改或拒绝；
3. 系统生成“模型可见上下文”预览；
4. 案主确认披露结果；
5. 授权审核人发布不可变版本；
6. 后续修改创建新版本。

所有个人研习、小组讨论、项目记录和个人项目测评都绑定当时的 `project_card_version_id`。新版本不得静默改变旧会话、旧答案或旧评价的依据。

## 5. 披露与 Agent 上下文

字段和材料统一使用：

```text
allow
mask
block
```

处理顺序：

```text
项目卡原始内容
→ 资源权限
→ model_policy
→ 脱敏或区间化
→ 上下文来源标记
→ 模型请求
```

禁止先发送完整数据，再依靠 Prompt 要求模型忽略。

项目讨论上下文只能由以下来源组成：

```text
项目卡已验证事实
+ 当前课程概念
+ 前序课程结论
+ 通用商业知识
+ 明确标记的新假设
```

输出来源必须区分：

| 来源 | 输出要求 |
|---|---|
| 已验证项目事实 | 使用“根据项目卡中的已验证信息……”并引用 fact ID |
| 前序课程结论 | 使用“在上一门课程的项目记录中……”并引用 conclusion ID |
| 通用商业知识 | 使用“从一般商业规律或课程框架看……” |
| Agent 新假设 | 明确说明项目卡暂无直接证据，并询问学员如何判断和验证 |

Agent 新假设只属于当前讨论，未经学员明确沉淀和后续核验，不得写入项目卡事实。

## 6. 个人项目测评题目合同

### 6.1 数量与发布

```text
每个课程 assignment：3-6 题
商业模式首发 assignment：6 题
正式提交次数：2 次
实时 Agent 帮答：禁止
数字总分：禁止
```

发布前冻结：

```text
course_id
project_id
project_card_version_id
question_set_version_id
rubric_version_id
question_count
questions
published_by
published_at
```

题目可以由教研直接配置，也可以由 AI 起草，但未经具名教研审核不得发布。

### 6.2 五类开放场景题

```text
fact_diagnosis
hypothesis_evaluation
option_comparison
causal_reasoning
judgment_revision
```

#### 事实判断

示例：

> 根据项目卡中现有信息，你认为当前最关键的商业模式问题是什么？请引用至少两条项目事实。

检验：

- 是否真正使用项目事实；
- 是否能定义核心问题；
- 是否只是套用通用框架。

#### 假设互动

示例：

> 一个可能的假设是：企业当前增长放缓并非获客不足，而是交付能力已经成为约束。你是否认同？请说明依据，并指出还需要补充什么信息。

检验：

- 是否能判断假设；
- 是否把假设误当事实；
- 是否具备证据意识。

#### 方案比较

示例：

> 如果企业在直营、加盟和联营中选择一种扩张结构，你会优先选择哪一种？请比较至少两种方案的关键资源要求和风险。

检验：

- 是否能比较方案；
- 是否理解资源、交易结构和风险的关系；
- 是否能作出取舍。

#### 因果推理

示例：

> 项目卡显示收入仍在增长，但利润率持续下降。请提出一条可能的因果链，并说明其中哪些环节已有事实支持、哪些只是推测。

检验：

- 因果链是否完整；
- 是否区分事实与假设；
- 是否跳过必要中间条件。

#### 判断修正

示例：

> 假设案主新增一条信息：“核心客户复购率很高，但新客户获取成本持续上升。”这条信息是否会改变你的原判断？为什么？

检验：

- 是否吸收新信息；
- 是否修正原判断；
- 是否僵化套用框架。

### 6.3 单题元数据

每道题至少配置：

```text
question_id
question_type
prompt
learning_objective_ids
course_concept_ids
scenario_fact_ids
introduced_hypothesis nullable
introduced_new_information nullable
minimum_fact_references
rubric_dimension_ids
required
display_order
```

`minimum_fact_references` 只在题目明确要求引用项目事实时使用，不对所有题机械设为 2。

## 7. 测评上下文与评价边界

学员作答页可以读取：

```text
冻结项目卡的允许字段
题目明确提供的新信息
必要课程概念
```

作答页不得提供：

```text
实时 Agent
个人研习历史
小组讨论历史
其他学员答案
评价量表内部判定提示
参考答案
```

评价模型可以读取：

```text
冻结题目
学员本次答案
冻结项目卡的模型可见上下文
当前课程概念
题目元数据
冻结量表
```

评价模型不得读取个人研习或小组讨论历史，也不得把通用知识或 Agent 推断写成企业事实。

## 8. 评价输出

统一六个评价维度：

```text
概念应用
项目针对性
事实与假设
因果与逻辑
方案与取舍
验证意识
```

每个维度使用：

```text
充分展示
部分展示
尚未展示
```

每个维度必须包含：

```text
level
answer_excerpt_ids
project_fact_ids
reason
next_action
```

报告结构：

```text
本次表现概述
做得较好的地方
需要加强的地方
事实与假设检查
判断修正情况
建议继续验证的问题
六维表现
```

禁止：

- 数字总分；
- 人格、潜力或创业适合度判断；
- 晋级、淘汰或资源配置结论；
- 没有答案片段和事实引用的空泛评语；
- 把未展示写成已经掌握。

## 9. 两次提交与异步评价

状态机：

```text
not_started
→ drafting
→ first_submitted
→ directional_feedback_pending
→ revision
→ final_submitted
→ final_evaluation_pending
→ completed
```

错误状态：

```text
directional_feedback_failed
final_evaluation_failed
```

约束：

- 草稿保存不消耗提交次数；
- 正式答案保存成功即消耗本次机会；
- AI 失败不回滚答案，不额外消耗机会；
- 重试使用同一幂等键，只生成一份评价；
- 第一次只提供方向反馈，不泄露参考结论；
- 第二次保存两次答案差异并生成最终评价。

## 10. 项目一致性

创建、保存和提交时必须同时满足：

```text
assessment_assignment.project_id
= project_card_version.project_id
= assessment_session.project_id

assessment_assignment.project_card_version_id
= assessment_session.project_card_version_id
```

标题相同、企业名称相同或同属一个小组都不能替代 ID 一致性。

## 11. 首发页面行为

### 11.1 项目卡

学员端按七个模块组织，不展示数据库术语。案主看到：

```text
保存草稿
预览模型可见内容
提交案主确认
查看退回意见
查看已发布版本
基于当前版本创建新版本
```

普通组员只能查看已发布且被授权的版本。

### 11.2 个人项目测评

页面提供：

```text
项目与项目卡版本
当前课程
题目进度
3-6 道开放题
冻结项目事实侧栏
保存草稿
正式提交次数
方向反馈或最终评价状态
```

页面不提供 Agent 入口，不显示内部 Prompt、模型、费用或量表判定提示。

## 12. 验收场景

### 项目卡

1. 案主可以完成七模块草稿并预览模型可见内容；
2. 后台导入后仍必须由案主确认；
3. 未确认版本不能发布或进入测评；
4. `block` canary 在模型请求、日志、评价和导出中零命中；
5. V2 发布后，V1 会话与测评仍引用 V1；
6. 非项目成员通过页面和直接 API 都无法读取项目卡；
7. 普通成员不能修改案主事实。

### 个人项目测评

1. 3 题和 6 题的合法 assignment 均可发布；
2. 少于 3 题或多于 6 题的 assignment 被拒绝；
3. 商业模式首发显示 6 题；
4. 全部 required 题完成前不能正式提交；
5. 草稿不消耗机会，两次提交后锁定；
6. 项目 ID 或项目卡版本不一致时拒绝；
7. 作答页没有 Agent 帮答入口；
8. AI 超时不丢答案、不重复计数；
9. 评价引用具体答案片段和项目事实；
10. 评价不显示数字总分，不读取个人或小组讨论历史。

## 13. 当前实现差距

[KNOWN, HIGH] 当前 L0 已实现：

- 麦客思草案项目卡只读预览；
- 项目卡和测评的 `project_id + project_card_version_id` 一致性；
- 商业模式固定 6 题；
- 草稿保存；
- 最多两次正式提交；
- 页面无实时 Agent；
- 固定方向反馈和固定最终反馈。

[KNOWN, HIGH] 当前尚未实现：

- 七模块案主填写和确认；
- PostgreSQL 项目卡版本；
- 后台导入审计；
- 企业材料对象存储；
- `allow/mask/block` 上下文生成器；
- 3-6 题配置校验；
- 题型元数据；
- 服务端异步 AI 评价；
- 六维证据化反馈；
- 跨设备恢复和正式权限。

当前 L0 页面只能用于交互审阅，不得描述为正式项目卡或正式 AI 评价。

## 14. Gate 顺序

本合同不改变 V6 Gate 顺序：

```text
先完成 Gate 1 身份、PostgreSQL 与权限
→ 完成 Gate 2 服务端课程进度
→ Gate 3 实现项目卡和讨论
→ Gate 4 实现个人项目测评和异步评价
```

在 Gate 1 未通过前，本合同只冻结产品和数据边界，不授权提前实现 Gate 3/4 正式页面。

## 15. 不确定性与遗漏

### 最没有把握

[KNOWN, HIGH] 正式案主、首发真实项目卡、企业材料授权和数据保留政策尚未提供。麦客思只能继续作为开发 fixture。

### 当前最大遗漏

[INFERRED, HIGH] 项目卡的主要风险不是字段不够，而是“谁确认、哪个版本、哪些内容能进入模型”没有形成可执行闭环。因此，案主确认、版本冻结和模型可见预览必须与七模块表单同时交付，不能只做录入页面。

[RULES I BROKE]: 无
